### Tier 3 — paths that still resolve while the body changed (10)

This is the half a path-level check structurally cannot see, and it is the larger half.

| Operation | Finding |
|---|---|
| `chat.create` | required body field **`spaceId` is never sent** |
| `chat.create` | sends **`projectId`**, which the schema does not define (`additionalProperties: false` → rejected) |
| `chat.update` | sends **`projectId`**, same rejection on `PUT /api/chats/{chatId}` |
| `space.create` | required body field **`providerOptions` is never sent** |

| `space.listFiles` | required query parameter **`pageSize` is never sent** (the call passes no `qs` at all) |

Two findings share one cause and it is worth naming: **chats moved from projects to spaces.**
`POST /api/chats` now requires `{ name, spaceId }` and accepts `origin`, `personaId`, `agentId`;
`projectId` is gone from the body, from `PUT /api/chats/{chatId}`, and from the `GET /api/chats`
query. The node still speaks the project-shaped dialect throughout. The URL never changed, so every
path-level report on this node has been green while `chat.create` could not have succeeded.

`space.create` is the same class: oneAI nested the per-provider fields under a `providerOptions`
object (an `anyOf` discriminated by provider), and the node still sends them flat.

### Tier 3 — warnings (2)

`chat.list` sends `projectId` as a query parameter on `GET /api/chats` from both of its call sites
(paginated and single-page). Unknown query parameters are ignored rather than rejected, so this is a
WARN, not a failure: the filter silently does nothing. The replacement is `spaceId`.

### Bugs found in the checker itself, by these tests

Recorded because they are the same failure class the tool exists to catch:

- The first run reported `unbalanced braces in switch (resource)` and exited 2 rather than reporting
  a surface. Cause: a `${…}` template interpolation's closing brace was decrementing the object
  brace depth. It failed loudly instead of reporting a plausible-looking wrong number.
- `modes.ts` reconciliation initially reported all 8 resources as missing from the registry. Cause:
  `RESOURCES: ResourceDefinition[] = [` — the parser anchored on the first `[`, which is the
  array-*type* suffix, not the array literal. **This one is the cautionary case**: it produced a
  confident, specific, entirely false finding, and only looking at it disproved it.
- The tier-1 "closest match" originally ranked `POST …/artifacts/{}/transfer` above the real
  successor `GET …/artifacts/{}/pdf`, because candidates under a shared prefix score identically and
  a method tie-break decided it. Replaced with a fact — the longest path prefix the spec still
  serves, and everything under it — instead of a ranking that invents a winner.

## 4. What this check **cannot** see

The list matters more than the findings. Everything below is currently unmeasured, and a green run
says nothing about any of it.

**Responses.** Only the request is compared. Every operation reads fields off the response
(`response.chats`, `responseData[itemsKey]`, `pagination.hasNextPage`); if oneAI renames a response
field, the request still validates, the path still resolves, this check stays green, and the node
returns empty or malformed items. `oneAiApiRequestAllItems` in particular depends on `hasNextPage` /
`totalCount` being present at the top level of the response, and that contract is unverified here.

**Staleness of the snapshot.** The guards catch a spec that is broken, truncated or absent. They
cannot catch a spec that is simply old — a valid six-month-old document produces a confident,
obsolete report. That is the entire reason `openapi/PROVENANCE.md` exists and must be updated with
the snapshot.

**n8n-side parameter names.** The node's UI property names (`name:` in the `description` array) and
what `execute()` reads via `getNodeParameter('…')` are never cross-checked. Per `CLAUDE.md`, a
renamed *parameter* breaks saved workflows **silently** — `getParameterIssues` does not validate
option membership. That is arguably the highest-value check this repository still lacks, and it is
not an API-drift question at all.

**Anything assembled outside the operation file.** The body reader resolves inline literals, a
`const body = {…}` with later `body.x =` assignments, and declared type annotations. A body built by
a helper in another module, or spread from a value it cannot read, is not checked. A spread
(`...x`) inside a body **suppresses** the "required field missing" check for that call, on purpose,
to avoid false positives — a deliberate blind spot.

**Values chosen at runtime.** Enum membership is only checked for string literals in the source. A
value the workflow author types into the node is invisible here.

**Semantic drift.** A field with the same name and type whose meaning changed is indistinguishable
from no change.

**Authorization and reachability.** Whether the credential in use can actually reach an endpoint —
`gatewayOnly` credentials, hub vs gateway routing, rights, tenancy, plan gates — is out of scope.
An endpoint can be in the spec and still 403 for every real user of this node.

**Literal-vs-parameter path routing.** Path matching is exact after normalising interpolations to
`{}`. If we called a literal segment that the server would route through a `{param}` path, this
would be reported as a missing path. No current call is in that position, but a future one could
produce a false failure.

**The floors are tripwires, not assertions.** `FLOORS.operations = 35` against a real 49 means that
legitimately removing a large resource will trip the guard and require a conscious edit. That is the
intended trade — see falsification row 3a, where a real 32 tripped it.

**Not run here:** `npm run lint`, `npm run build` and `npx @n8n/scan-community-package`. This
checkout has no `node_modules` and none was installed, since `package.json` was not to be touched.
Nothing under `nodes/`, `credentials/` or `package.json` was modified, `scripts/` is outside the
`tsconfig.json` `include`, and only `dist` is published — so none of those gates has new input. They
still have to be run before any release claim.

## 5. Note on the gate command

`CLAUDE.md` lists the gate as `node scripts/drift-check.ts`. The script is
**`scripts/drift-check.mjs`**. This is deliberate, not an oversight:

- this repository has **no committed lockfile and no `node_modules` in a fresh clone**, so a checker
  that needs `tsx` or the `typescript` package only runs after a successful install;
- CI pins **Node 22** (`.github/workflows/publish.yml`), where `node foo.ts` type-stripping is not
  dependably on.

A drift check that silently stops running is worth less than no drift check, so it is plain ESM with
zero dependencies and runs on any Node ≥ 18. **The `CLAUDE.md` gate line should be corrected to
`.mjs`** — it was left unedited here because it is instruction substrate and not in this task's scope.
