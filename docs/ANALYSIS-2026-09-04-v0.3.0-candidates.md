# What should go into v0.3.0 — pre-analysis and recommendation

**Written 2026-09-04**, after `0.2.0` was published to npm with provenance and live-traced on the
bench at `n8n.oneai.de`. Requested by the owner as a pre-analysis before planning the next release.

Two agents ran independently: the **architect** (which capabilities should become operations, judged
as a workflow author) and a **coverage map** (pure measurement, forbidden from recommending
anything). Running them separately was deliberate — it gives a way to check the proposal against
measured facts instead of trusting it. Every load-bearing claim below was then re-verified by hand
against `openapi/openapi.json` or against n8n's own shipped source; the few that could not be are
labelled `INTERPRETED`.

---

## The baseline, measured

| | |
|---|---|
| Spec snapshot | **325 paths / 401 operations** (`openapi/openapi.json`) |
| Shipped, dispatched from `router.ts` | **64 operations / 11 resources / 79 API calls / 0 parked** |
| Distinct spec operations covered | **61 (15.2%)** |
| Spec groups with any coverage | 10 of 44 |

Two independent extractors agree exactly on the covered set — `scripts/drift-check.mjs --json` and a
from-scratch parser written for this analysis — with a symmetric difference of ∅. The gap between
64 dispatched and 61 distinct is not an error: `project:archive` and `project:unarchive` share
`POST /api/projects/bulk`, and `datasetRow:appendMany` is dispatched outside the per-item loop.

🔴 **15.2% is not the finding, and closing it is not the goal.** The measure is composability. Most
of the remaining 340 operations should never be node operations, and the rejection list below is the
more useful half of this document.

---

## Three findings that close doors

These matter more than the candidate list, because each one removes an option that looks obvious
from the outside — and one of them was my own.

### 1. 🔴 A webhook-based trigger node is impossible

**All 11 `api/webhooks` endpoints are receivers.** Every one of the 11 `summary` fields begins with
the word *"Receive"*. The document declares `"openapi": "3.1.1"` but has no top-level `webhooks`
object, and **zero of the 401 operations carry a `callbacks` object**. `callbackUrl`,
`notificationUrl`, `targetUrl` and `text/event-stream` occur **0 times**. The six `webhookUrl` hits
are oneAI telling *you* which address to paste into a provider's dashboard.

**No endpoint in the API registers a URL for oneAI to call back**, so n8n's `webhookMethods` shape
has nothing to attach to. `POST /api/webhooks/n8n` is oneAI receiving *from* n8n — the arrow already
points n8n → oneAI.

A **polling** trigger remains possible (`polling: true` makes n8n's loader inject the Poll Times UI
itself). `GET /api/audit/logs` is the only pollable event with a server-side cursor, and even it has
a trap: `since` is *"clamped to the plan's retention window"*, so a workflow stopped over a long
weekend silently loses events rather than catching up.

*Limit worth stating:* an OpenAPI document describes a server's own routes. This is strong evidence
that **the spec describes no outbound path** — not proof the product has none. Settling that needs
the platform source or a live instance.

### 2. 🔴 An agent run takes no input

`POST /api/agent-definitions/{agentId}/runs` has request body
`{"type":"object","properties":{},"additionalProperties":false}` — **required, and empty**.

So the attractive story *"one agent run per input item, with this item as the prompt"* **is not
available**. Whatever we build on Agent Builder has to be honest about that: n8n starts and
supervises a run, it does not parameterise one. This is exactly the kind of constraint that would
have surfaced as a runtime surprise three weeks after shipping.

### 3. 🔴 `usableAsTool` cannot hide an operation from the AI-tool variant

Verified in n8n's source at `4b0de25a`:

```ts
export type UsableAsToolDescription = {
	replacements?: Partial<Omit<INodeTypeBaseDescription, 'usableAsTool'>>;
};
```

`INodeTypeBaseDescription` carries `displayName`, `name`, `icon`, `group`, `codex`, `hidden` … and
**no `properties` field** — that lives on the extended `INodeTypeDescription`. There is therefore
**no mechanism to expose an operation on the main node but withhold it from `oneAiTool`**. It is all
or nothing, per node.

That matters here because two proposed operations are *approval verdicts* — `agent:confirm` and
`auditLog:review`. Shipping them makes "an LLM approves the action" reachable in one hop.

**Precedent, measured rather than assumed:** n8n's own `SlackV2` node is `usableAsTool: true` and
exposes `archive`, `kick`, `delete`, `deleteScheduled` and `disable` through the tool variant. So
destructive operations in a tool surface are n8n's normal practice, and the workflow author chooses
which nodes become tools. **Recommendation: ship them, name them unambiguously, and say so in the
README** — but flag it to the owner rather than deciding it quietly, because oneAI is a compliance
platform and an approval verdict is a different class of act from deleting a chat message. It is
also the reason `PUT /api/compliance/llm` is rejected outright below: an LLM able to disable the
org's compliance layer has no compensating workflow value.

## Candidates, ranked

### A1 — Finish the loops we already opened *(highest confidence, lowest risk)*

Two capabilities shipped in `0.2.0` are **half-built**, and that reads as a defect rather than a
missing feature.

**Ingestion has no completion signal.** The node ships `space:uploadFile`, `space:embedFiles` and
`space:sync` — and **no way to learn whether any of them finished**. Missing:
`GET …/files/stats` (embedding status counts), `GET …/files/extracted`, `GET …/files/folder`,
`POST …/files/cancel-embed`. Without `stats`, "upload a file, then chat against it" is a race the
author can only lose by guessing a Wait duration.

*(Measured, after an earlier claim of mine that the file surface was entirely uncovered was wrong:
6 of the 11 `/files` endpoints are covered — `files`, `download`, `delete`, `upload`, `transfer`,
`embed`.)*

`GET …/files/extracted` returns *"the verbatim extracted Markdown text of a file"*. That is a
composition story in its own right: **oneAI becomes a document-extraction service inside n8n** —
PDF from Google Drive → oneAI → Markdown → any of hundreds of downstream nodes. It is a better
extractor than n8n's own "Extract from File" for the formats oneAI already handles.

**Generated images are unreachable.** `ai:createResponse` can produce an image blob, and the node
offers no operation to fetch it. `blobId` appears **0 times** in the `/api/chats/{chatId}/http`
response and **twice** in `GET /api/chats/{chatId}`, as part of a `{type:'blob', blobId, mimeType,
prompt, revisedPrompt, model}` union member — so `chat:get` is the discovery path, and the operation
descriptions must say so, or an author will conclude the feature is broken. Add
`chat:getBlob` / `getBlobUrl` / `saveBlobToSpace`.

### A2 — The chat loop *(the owner's "very important" surface)*

`chat:export` (`{filename, markdown}`, JSON not binary) → Notion, Confluence, Google Docs.
`chat:rateMessage` → a 👍/👎 a human gives in Slack lands in oneAI's feedback store.

🔴 `chat:export`'s `full=true` returns values that compliance redaction removed. **The default must
be `false`**, and the parameter needs a description that says what it does.

### A3 — Agent Builder *(the largest genuinely new capability)*

Resource `agent` over `/api/agent-definitions` (16 endpoints; propose ~7): `list`, `get`, `run`,
`getRun`, `listRuns`, `listPending`, `confirm`.

**The composition story:** *Schedule Trigger → `agent:run` → `agent:getRun` in a Wait loop →
`agent:listPending` → Slack `sendAndWait` → `agent:confirm`.* A oneAI agent's tool-call approvals
leave oneAI's UI and land in Slack, Teams or email. That is impossible today, and the neighbour is
shipped and maintained by n8n (`SlackV2` imports `utils/sendAndWait/*`).

Second, independent reason: **`chat:create` and `chat:update` already ship an `agentId` parameter,
and the node offers no way to obtain one.** `GET /api/agent-definitions` alone repairs a dangling
parameter we shipped.

Subject to finding 2 — a run cannot be parameterised.

### A4 — The compliance loop

`auditLog:review` (`outcome: block|unblock`, `text` maxLength 80) and `auditLog:export` (ZIP, needs
`oneAiApiRequestRaw`). The field that makes it a workflow already exists in what we return:
`logs[].summary.reviewRequired`. There is no server-side filter for it — n8n's Filter node is the
neighbour, which is the right division of labour.

### A5 — `oneAI Chat Model` sub-node *(strategic; the owner's call, not mine)*

One sub-node of roughly 150 lines would make **every AI Agent, LLM Chain and Information Extractor
in n8n** run on oneAI. In reach, nothing else on this list compares.

The first read was that this is blocked because oneAI exposes no `/chat/completions` — and it does
not; there are exactly 7 `api/openai` paths and that is not among them. But
**`POST /api/openai/v1/responses` exists** and accepts `input`, `instructions`, `model`, `stream`,
`stream_options`, `tools`, `tool_choice`, `parallel_tool_calls`, `store`, `temperature`,
`reasoning`, `text` … with `200` in both `application/json` and `application/octet-stream`.
LangChain's `ChatOpenAIResponses` targets exactly that API. **Feasible today**, on paper.

Two costs, both real:

- 🔴 **It would introduce the first runtime dependencies into a zero-dependency package.** That is
  not a detail here: `CLAUDE.md` records that the publish path builds `dist/` in the release job
  from dependencies resolved that minute, so what ships is not provably what was tested. Zero
  runtime dependencies is currently the property that keeps that acceptable.
- 🔴 `additionalProperties: false`, and **`previous_response_id` is absent from the accepted list**.
  The spec is already telling us the model must send full history on every turn rather than pointing
  at stored state.

**Do not fold this into v0.3.0 on paper.** Settle it with one spike whose only deliverable is a
single live tool-calling round trip against devtest. If it works, it is probably the most valuable
thing this package could ship next. If it fails on a property `additionalProperties: false` rejects,
it is a **platform request to the oneAI team**, not node work — and knowing which costs an afternoon.

## Rejected, and why

The half a reviewer cannot reconstruct from the selection alone.

| | why not |
|---|---|
| **`api/spaces`, 38 uncalled** | **27 of 38 (71%) are connector-setup wizards for one named third party** — github, onedrive, smb, clickup, weclapp, forgejo, hubspot, outlook. Rejected not for being administrative but because **n8n already ships a better node for every one of those providers**. `POST /api/spaces/n8n/validate` is rejected for being circular. |
| **`api/mcp` — reject and *document* instead** | `POST /api/mcp` is oneAI's MCP JSON-RPC endpoint, and n8n ships `McpClientTool` / `McpClient` / `McpTrigger`. **An author can already give an n8n AI Agent oneAI's tools without this node existing.** Wrapping it would be strictly worse than a paragraph in the README. |
| **Agent Builder `triggers` (5)** | server-enforced **15-minute minimum interval**; n8n's Schedule Trigger has no floor and sits in the same canvas. `Schedule Trigger → agent:run` supersedes the family. |
| **`api/uno` (8)** | creatable, listable, deletable — and **no endpoint to send a message**. A resource whose only verb is "delete" is not a workflow. |
| **`api/integrations` (33)** | no n8n node can be named that sits on either side. That inability *is* the finding. |
| **`api/user-keys`, `POST /api/agents`** | rejected on **security**, not scope: they mint credentials (*"plaintext token returned exactly once"*) directly into n8n's persisted execution history. |
| **`PUT /api/compliance/llm`** | see finding 3 — an LLM could disable the org's compliance layer. |
| **`auth`, `passkeys`, `subscription`, `scim`** | out of scope by the owner's standing instruction. Not re-litigated. |
| Artifact editor surface (24 of 28), `api/public/*`, presentation templates, teams/members/orgs, private-models | no composition story found. Org provisioning is the most defensible of these if the owner wants it. |

## Recommendation

**v0.3.0 = A1 + A2 + A3 + A4.** Roughly 20 operations, one new resource (`agent`), no new node file,
**no new dependencies, and no new `typeVersion`** — every item is an added operation or an added
optional parameter, which is safe under `typeVersion: 1`.

The release has a shape worth stating in that order: **first finish the two loops `0.2.0` left half
open** (ingestion without a completion signal, generated images with no way to fetch them), *then*
add the new surface. A user who hits the half-open loops experiences them as bugs, and they cost
less to close than anything else on the list.

**Run the A5 spike in parallel, as a separate investigation that the release does not wait on.**
Its one question — does `ChatOpenAIResponses` complete a tool-calling round trip against oneAI —
is worth more than any single operation proposed here.

**No trigger node in v0.3.0.** Not because polling is unattractive, but because a trigger that starts
a workflow which cannot then finish is worth nothing; A3 and A4 are what make one worth building.
🔴 And a prerequisite regardless: `scripts/panel-check.mjs` hard-codes `OneAi.node.ts` and
`OneAi.node.json` (lines 54–55), so a second node file would be **invisible to the checker that
exists to keep this node findable**. Extending it to walk `package.json`'s `n8n.nodes` array comes
before any second node, not after.

## Open questions for the owner

1. **A5** — is trading the package's zero-dependency property for reach across every n8n AI Agent a
   trade you want? The spike settles feasibility; it does not settle this.
2. **Finding 3** — ship `agent:confirm` and `auditLog:review` as AI-callable, matching n8n's own
   practice with Slack, or hold the approval verdicts back?
3. Anything in the rejection table you read differently — particularly org provisioning.

## Verification still owed before implementation

- Does `GET …/files/extracted` work **before** embedding completes, or only after? One live devtest
  request. If only after, `files/stats` stops being a nicety and becomes a required companion.
- The spec is a snapshot of oneAI commit `f2b70d0c…` taken 2026-09-03. Anything merged into the
  platform since is invisible here **by construction** — re-snapshot before implementing.
- 3 of 79 request bodies are `bodiesOpaque` in the drift report, so its clean result does not cover
  them.
